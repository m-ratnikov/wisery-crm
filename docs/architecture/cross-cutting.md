# Cross-cutting concerns

System-wide concerns at the L1 boundary - where each lives and which decision fixes it.
Technology mechanisms (the logging library, the job queue, connection pooling) are L2
choices; this file names the concern and points to the deciding ADR.

Related: [system-context.md](system-context.md), [system-design.md](system-design.md),
[product-overview.md](../product-overview.md), [ADR-0001](../adr/0001-background-job-runtime.md),
[ADR-0002](../adr/0002-headless-browser-scraping.md), [ADR-0003](../adr/0003-llm-provider-port.md),
[ADR-0004](../adr/0004-pg-boss-facade.md). Promoted from change `system-context-c4-l1` (2026-05-22);
L2 references added by `c4-level2-architecture` (2026-05-24); the on-demand generation / scoring
provenance notes added by `engagement-rework` (2026-06-08), then the scoring notes removed by
`adr-signal-only-scoring` (2026-06-13: person scoring gone, the signal advisory is the only score,
ADR-0022).

- **Observability**: structured logging with dead-letter visibility from logs and SQL views over the job tables - no job dashboard UI (the logging library and queue are L2 technology choices; ADR-0001). The engagement/triage handlers (advisory-filter, activity-scan, fetch-posts) surface in the existing jobs monitor; comment generation is a synchronous server action, observed via request logging rather than the jobs monitor (content-marketing-engagement).
- **Configuration**: per-user ICP/profile/sources are config-as-data (D6); runtime config and provider endpoints via environment.
- **Secrets**: API keys for the scraping/enrichment provider and the LLM provider (provider-agnostic behind the `LLMProvider` port, D9), plus the Postgres connection strings, live server-side only and never reach the client bundle (server-only). On the self-host browser path, scraping session material lives in the browser's OS process (ADR-0002). Connection and pooling specifics are an L2 concern (ADR-0001).
- **Failure handling**: external calls (the scraping/enrichment provider, the LLM provider) run as durable background jobs with retries and a dead-letter path (ADR-0001 fixes the mechanism); a single source scan that fails is isolated and does not affect other sources; a self-host headless-browser crash is contained in its own OS process (ADR-0002). Stage-to-stage handoffs are atomic: a stage enqueues the next stage's job inside the same Drizzle transaction as its state write (pg-boss's `fromDrizzle` adapter), so a committed transition can never be stranded without its follow-on job ([ADR-0009](../adr/0009-atomic-enqueue-handoff.md)). This requires pg-boss to share the app's Postgres database (the default); a separate pg-boss database forfeits the atomicity and is unsupported for the atomic handoff. The on-demand Person actions (generate a message or comment, enrich) are synchronous server actions rather than durable jobs: an LLM/enrichment error surfaces to the user on that action with no pg-boss retry and no idempotency key, each call writing one row (ADR-0018, generalized to Message by ADR-0019); signal approval creates the entity, writes no score, and enqueues nothing, so it has no downstream job to strand (ADR-0022).
- **Trust boundaries**: every external call is server-side; inbound third-party data (sources, enrichment) is untrusted and normalized at the edge (D4). Auth/sessions are deferred while single-user (D1); the CRM user is the only trusted principal today.
- **Data sensitivity**: third-party prospect PII enters from signal sources and any scraping/enrichment provider, is stored in Postgres, and is sent to the LLM provider for advisory scoring and generation - the main data-processor exposure; the PII surface spans whichever provider is selected (D9), and field minimization attaches at the qualify boundary when productized (D10). Within the data model the PII concentrates in the runtime entities - the Signal payload, the advisory `reason` on the signal, the Dossier, and (from the engagement motion) a person's Posts, the AI-drafted Comments, and the on-demand LinkedIn Messages (ADR-0021). Dropping person scoring (ADR-0022) removes the former `scorings.reason`/`summary` strings (LLM judgments about a person) from that surface, marginally shrinking the stored derived-PII. Message bodies are third-party-directed PII held server-side behind the same boundary as Comment and Dossier, and no content is published automatically - the human posts every message and comment (D2). The only outbound path to the Prospect or engagement target is the manual human action.
- **Learning loop (D7), deferred**: the outcome-driven learning loop is not built and is re-grounded on the signal advisory, not per-person scores (ADR-0022). With person scoring removed there is no `scorings.provenance` seam and no `outcomes.score_at_time` snapshot; outcomes are logged against the person and the artifact only. The forfeit is named: today's `signal_advisory` is a mutable, version-unpinned hint (refreshed in place by the job, recording `rubric_kind` but no rubric version or provenance), so it is not learning-grade. When D7 is designed it must introduce its own append-only, rubric-version-pinned, provenance-carrying record (or make the advisory snapshot-at-decision durable); the old provenance-exclusion invariant is gone, moot now that the cheap advisory pass is the only score there is.
- **Scaling / capacity**: background work runs in-process now, with a no-rewrite path to a standalone worker if request latency degrades (ADR-0001). The binding constraints are the paid, rate-limited externals (the scraping/enrichment provider when used, the LLM provider) - cost per call and throttling, which the design gates and tolerates rather than scales past.
