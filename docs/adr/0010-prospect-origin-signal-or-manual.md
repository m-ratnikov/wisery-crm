# ADR-0010: A prospect originates from a signal or is entered manually

- Status: accepted, supersedes ADR-0005
- Date: 2026-06-03
- Supersedes: ADR-0005
- Source: docs/architecture/domain-model.md (Entity model, Prospect), this change's domain-model.md and use-cases.md

## Context

ADR-0005 decided the signal-to-prospect relationship as one-to-many and, in doing so, fixed that "a `Prospect` references exactly one `Signal`" - which the data model expressed as `prospects.signal_id NOT NULL`. That totality is correct for the pipeline's discovery path (every scraped or expanded person traces to a signal) but it forecloses a real CRM-user goal: adding a person they already know - a referral, a contact from an event, a name from a call - with no upstream signal behind them (use-cases UC1). Because Drizzle migrations are immutable once applied, the nullability of `signal_id` is decided once; relaxing it later for manual entry would otherwise be a costly migration on the pipeline's central table. The fan-out cardinality itself (one signal to many prospects) and the score-per-person decision remain correct and are not in tension - only the claim that every prospect must have a signal is. This ADR therefore supersedes ADR-0005 scoped to that totality clause only: ADR-0005's other decisions are left in force by reference, not restated here, so the cardinality rule keeps a single home and the supersedes chain records only what actually changed.

## Decision

We will model a `Prospect` as having an **origin**: `signal` (the existing path) or `manual` (entered by the CRM user). ADR-0005's decisions other than the totality remain in force unchanged and are referenced rather than restated: the one-to-many signal-to-prospect fan-out, the per-person `Scoring` (score against the prospect, never the shared signal), and per-source dedup. Cross-source identity resolution - now also cross-origin (a manual lead duplicating a signal-derived person) - stays out of scope and deferred.

Newly decided here: a `Prospect` references **at most one** `Signal` - exactly one when `origin = signal`, none when `origin = manual` - so `prospects.signal_id` becomes nullable. `origin` is `text` validated by a Zod enum (beside `status`, and plausibly extensible at productization, for example `import`/`api`), defaulting to `signal` so the migration is additive and every existing row reads as signal-derived with no backfill. A manual prospect's person identity (`name` required, plus `headline`, `company`, `linkedin_url`) lives in columns on the prospect; a signal-derived prospect leaves them null and its identity is read from `signals.payload` as today, both surfaced through one `PersonIdentity` read seam that confines the origin branch to a single place (the footprint this creates in the signal-keyed pipeline is in Consequences). The origin invariant is enforced by a DB CHECK, expressed per-origin so a future origin does not trip it: `(origin <> 'signal' OR signal_id IS NOT NULL) AND (origin <> 'manual' OR (signal_id IS NULL AND name IS NOT NULL))` - `origin = 'signal'` forces the signal present (the thing ADR-0005's NOT NULL guarded stays impossible) and `origin = 'manual'` forces no signal and a name. It deliberately does not pin the manual identity columns null for signal rows, leaving room for a future cross-origin merge to write a resolved name onto a signal-derived prospect.

## Consequences

Easier: the CRM user can put a known person under evaluation with no source wiring; once added it flows through qualify, enrich, draft, and the queue under the same rubric gate, the same insufficient-data verdict for a thin lead, and the same learning loop. Existing data is untouched: the migration is additive and `origin` defaults to `signal`, so no row is rewritten and the discovery path is unweakened. Cost accepted - this is NOT a no-op on the pipeline: because the pipeline is signal-keyed today, the implementing (separate, `spec-driven`) code change must introduce a `PersonIdentity` DTO read from a signal or from prospect columns through the one seam, replacing the direct `SignalRow` dependency in the scorer, the drafter, and `loadActionableProspect`; add a prospect-keyed qualify entry and idempotency (the existing entry is signal-keyed and creates the prospect itself); change the prospect-list and queue read-models from inner to left join so a manual prospect is not dropped; and add a re-qualify action so a manual prospect whose fire-and-forget enqueue failed (it sits in `new`) can be re-driven. Person identity also now has two homes (signal payload vs prospect columns) reconciled by the seam - the cost of keeping the origin branch in one place rather than spread across consumers. Rules out: a signal-derived prospect without its signal (the CHECK forbids it). Because this ADR supersedes ADR-0005's totality clause, a reader follows the supersedes chain to the in-force cardinality, which lives unrestated in ADR-0005; ADR-0005 stays immutable and unedited.
