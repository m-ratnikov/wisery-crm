# ADR-0019: Generation and scoring are on-demand Person actions, not auto pipeline stages

- Status: accepted - owner sign-off 2026-06-08
- Date: 2026-06-08
- Supersedes: ADR-0013 (in part - the post-approval `qualify` enqueue and its "never stranded" handoff), ADR-0007 (in part - the auto-enrich-on-`ProspectQualified` setting), ADR-0017 (in part - its "only the post-approval qualify step persists a Scoring" mechanism; its no-learning-loop-pollution purpose is preserved via the `advisory` provenance exclusion), ADR-0010 (in part - its "a manual prospect flows through qualify the same as a signal-derived prospect" auto-score decision)
- Refines: ADR-0005 (its mandated per-person Scoring is now created by approval-promotion + on-demand re-score), ADR-0018 (synchronous-generation principle, generalized to Message and re-score)
- Source: docs/explore/2026-06-08-engagement-rework-queue-pipelines-messages.md; docs/architecture/system-design.md (Decisions and trade-offs)

## Context

The content-marketing model kept first-touch drafting as an automatic pipeline stage: approving a person signal enqueued `qualify`, which on a qualifying score enqueued `draft`, which produced a one-selected `Draft` and moved the person to a `queued` status feeding a Review & approve queue. The product owner rejected this on review: message generation is a high-judgment action the user takes on a specific person, not a funnel position every qualified person is pushed through, and an automatic draft spends LLM budget on people the user may never contact. The system already has the right pattern in hand: the comment generator is a synchronous user-triggered server action that writes one row per call, with no pg-boss job, no idempotency key, and no retry that could double-bill (ADR-0018).

A created person should keep the assessment it already earned: the owner's directive is that a person created from the Queue carries its initial score, rather than starting blank. The advisory pass scored the signal at triage but wrote no `Scoring` (ADR-0017, so the cheap pass never pollutes the learning loop). A naive "copy the advisory row into a Scoring" fails the entity contract - `signal_advisory` has a nullable `score`, a `rubric_kind`, and no `rubric_id` / provider / prompt_version / model, whereas `scorings` requires a NOT NULL `rubric_id`, a NOT NULL `score`, and the NOT NULL `provider`/`prompt_version`/`model` provenance columns, with no way today to distinguish an advisory-seeded row from an LLM-scored one. The viable form is a proper promotion at the human approval moment, plus a schema addition that makes the advisory row distinguishable so it can be kept out of the learning loop. Conversely, a hand-created person has no signal and no advisory, so there is nothing to promote and no reason to spend an LLM call scoring it unasked - manual entry should not auto-score.

## Decision

We will make all post-intake intelligence on-demand Person actions, removing the automatic drafting stage entirely, and unify scoring on two triggers: a no-LLM promotion at approval and a synchronous on-demand re-score.

- **Remove the drafting stage**: delete the drafter, the draft prompt, the `qualify -> draft` and `enrich -> re-draft` enqueue handoffs, the `draft` worker/queue, the `queued` status, and the Review & approve queue surface. The `Draft` entity (per-prospect, one-selected) is retired; first-touch is a Message generated on demand (ADR-0021).
- **Generation is synchronous and user-triggered**: generating a Message or a Comment, re-scoring, and enriching are server actions invoked from the Person workspace, each writing one row per call through the existing port (`LLMProvider` for generation/scoring, `EnrichmentProvider` for enrich), surfacing errors to the user with no background retry. This generalizes the ADR-0018 comment pattern to Message and re-score.
- **A `scorings.provenance` column distinguishes advisory-seeded rows**: add `scorings.provenance` (`llm | advisory`, NOT NULL default `llm`; a Zod-closed set). It is the single seam the learning-loop exclusion keys on. An `advisory` row stamps a stable sentinel into `provider`/`prompt_version`/`model` (all `advisory`) so the existing NOT NULL contract holds with no LLM call.
- **Approval promotes the advisory score into the person's initial assessment Scoring (no LLM), when a rubric exists**: `approveSignal` stops enqueuing `qualify`. In the one transaction that writes the `SignalDecision` and creates the routed `Person` (person- or peer-type only; a company signal creates a `Company` and no Scoring, per ADR-0017's company-rubric-no-Scoring exception), it resolves the active rubric of the advisory's `rubric_kind` and, **if one exists**, writes one initial `Scoring` - that `rubric_id`, `score` = the advisory score (or -1 if absent), `provenance = advisory`, no LLM call. If no active rubric of that kind exists at approval (e.g. no `peer` rubric is seeded yet), no Scoring is written and the person reads `unassessed` until a rubric exists and the user re-scores - the approval never fails on a missing rubric. So a Queue-created person keeps its initial assessment score as a first-class, queryable property whenever the rubric to express it exists.
- **Manual entry writes no Scoring (no auto-score)**: a hand-created person (ADR-0010, origin = manual) has no advisory to promote; it starts unscored and is scored only when the user clicks re-score.
- **Qualification is a read over the latest in-kind Scoring**: a `prospect`-type Person is `qualified` (latest `icp`/buyer-rubric Scoring >= 3), `below_bar` (< 3, where the `-1` insufficient-data sentinel is classified `below_bar` by rule, not by arithmetic - distinct from `unassessed`), or `unassessed` (no `icp`-rubric Scoring row at all - a manual person before its first re-score, or a Queue person approved before any `icp` rubric existed). The read is the latest Scoring **of the buyer/`icp` rubric kind**, by `scored_at`, tie-broken by `id` - the rubric-kind filter is part of the read, so a non-buyer (peer) row never satisfies a buyer qualification. A Queue-created prospect is assessed from creation via the promoted initial Scoring. A `peer`-type Person is `n/a` for buyer qualification (never buyer-scored, ADR-0017); its initial Scoring is the peer-rubric assessment, and the on-demand re-score is offered only on prospect-type Persons.
- **Re-score is the single on-demand scoring action; the `qualify-prospect` worker is retired**: the three current producers of the `qualify-prospect` queue - the approval-path `enqueueQualifyProspectInTx`, the manual-entry `enqueueQualifyProspect`, and the `reQualifyAction` recovery action - are all removed or converted to the synchronous re-score, so no path enqueues durable scoring and the `qualify-prospect` pg-boss worker is removed. Re-score is a synchronous server action that writes a fresh `icp`-rubric `Scoring` (`provenance = llm`, LLM call) superseding the initial assessment; reads take the latest in-kind by `scored_at` (tie-broken by `id`). The `advisory` and `llm` rows coexist permanently (additive, never pruned), so every qualification read and eval filters by provenance + rubric kind, never "the Scoring". It carries no singleton/already-scored guard, so two fast clicks write two rows - accepted (re-score is rare, newest-row-wins).
- **Enrichment trigger relocates to the Person workspace; the auto-enrich-on-qualify setting is removed**: enrichment stays user-triggered and optional (ADR-0007's core), but its trigger surface is the Person workspace, and the per-tenant auto-enrich-on-`ProspectQualified` setting is withdrawn because the `ProspectQualified` event it hung on no longer exists. A future auto-enrich-on-re-score may reintroduce it; that is a later decision.
- **Batch first-touch is out of scope for v1**: generation is single-person and synchronous in v1; generating for many approved people at once is a named follow-up, not silently dropped. If batch returns it reuses the ADR-0009 fire-and-forget facade path (as batch-enrich does), not a revived auto stage.

## Consequences

Easier: LLM and Apify spend is incurred only on an explicit user click (the cost-control attribute) - approval's initial Scoring is a no-LLM promotion of an already-computed advisory score; a committed approval enqueues no downstream job, so the ADR-0009 handoff has nothing to strand for the approval path. The drafting code/prompt/worker/review surface and the entire `qualify-prospect` worker are deleted, shrinking the system to one synchronous scoring path plus the no-LLM approval promotion. Harder/accepted: the `scorings` table gains a `provenance` column and an `advisory` sentinel convention; the `advisory`-provenance initial Scoring is a cheaper, lower-confidence assessment than an LLM re-score, so the qualification read and every eval must filter by provenance and rubric kind; a manual person is genuinely `unassessed` until its first re-score, as is a Queue person approved before its kind's rubric existed. Removing the `draft` and `qualify-prospect` workers leaves their pg-boss queues orphaned in Postgres, so promotion carries one-time `deleteQueue("draft")` and `deleteQueue("qualify-prospect")` runbook steps (the change's deployment.md). The `Draft` entity is retired as a generation target, but the `drafts` table is left in place (frozen, no new rows) because `outcomes.draft_id` still references it - dropping it would break historical outcomes; binding a tracked `Outcome` to the `Message` that drove it (a nullable `outcomes.message_id`) is deferred with the rest of the outcome/learning-loop work.

**Learning-loop integrity (preserving ADR-0017's purpose).** The D7 learning loop must never train on the cheap advisory pass. Two exclusions enforce this: `advisory`-provenance `Scoring` rows are excluded from the loop by the `provenance = 'llm'` filter; and because an `Outcome` snapshots `score_at_time` from whatever score was current when the user acted (and an `Outcome` carries no provenance of its own), an `Outcome` logged against a person whose latest in-kind Scoring is `advisory`-provenance must likewise be excluded from bar-tuning - recorded by carrying the bound score's provenance onto the outcome read, or by nudging the user to re-score (one click) before a tracked touch. The exact D7 query is future work (the learning loop is not built in these slices), but the invariant is fixed here: an `advisory` score never tunes the bar, through either table.

This **supersedes in part** four accepted ADRs and leaves the rest of each in force: from ADR-0013, only the post-approval `qualify` enqueue and its "never stranded" handoff are withdrawn - ADR-0013's universal human gate, no-per-source-bypass, advisory-not-auto-gate, and fan-out-on-approval decisions all stand. From ADR-0007, only the auto-enrich-on-`ProspectQualified` setting is withdrawn - enrichment-is-user-triggered-and-optional stands. From ADR-0017, only the "only the qualify step persists a Scoring, the advisory writes none ever" mechanism is withdrawn - approval may now persist an `advisory`-provenance Scoring, but ADR-0017's purpose (the advisory must not pollute the ADR-0005 learning loop) is preserved by the exclusions above; ADR-0017's type-keyed advisory rubric selection (icp/peer/company) and its company-rubric-no-Scoring exception stand unchanged. From ADR-0010, only its "a manual prospect flows through qualify the same as a signal-derived prospect" auto-score decision is withdrawn - ADR-0010's manual origin, nullable `signal_id`, the PersonIdentity seam, and the one-to-many fan-out all stand. It **refines** ADR-0005 (its mandated per-person Scoring is now created by approval-promotion + on-demand re-score, not a qualify job - the trigger timing that ADR-0013 set is what the ADR-0013 partial supersession withdraws) and ADR-0018 (the synchronous-generation principle extends to Message and re-score). The canonical `DraftGenerated`, `PersonQueued`, and the `PersonQualified` event (previously emitted by the `qualify-prospect` worker after approval) and the `Qualified -> Queued` lifecycle edge are removed at promotion.
