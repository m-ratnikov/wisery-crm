Where things run does not change: the in-process worker on managed Postgres (ADR-0001) is unchanged - no new host, datastore, secret, or network boundary.

The only deploy-time consequence is one **additive** Drizzle migration: `prospects.signal_id` becomes nullable (a metadata-only `DROP NOT NULL`, no table rewrite, no FK re-declaration), plus `origin` (text, default `signal` - a constant default stored in catalog metadata on PG 11+, so no rewrite), the manual identity columns (`name`, `headline`, `company`, `linkedin_url`, all nullable, no default), and the per-origin CHECK constraint from [domain-model.md](domain-model.md). Defaulting `origin` to `signal` means existing rows need no backfill, and they satisfy the CHECK (signal-origin with `signal_id` present). Note for the code change: `ADD CONSTRAINT ... CHECK` validates existing rows under an `ACCESS EXCLUSIVE` scan; at MVP scale this is negligible, but if the table is ever large the constraint can be authored `NOT VALID` then `VALIDATE CONSTRAINT` (taking only `SHARE UPDATE EXCLUSIVE`) by hand-editing the generated migration. That migration is authored and shipped by the separate `manual-lead-entry` code change (no code or migration ships from this architecture change), applied through the existing `db:migrate` path. Migrations remain immutable once applied (a later change is a new migration).
