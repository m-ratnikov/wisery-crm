# ADR-0006: Maintain a pre-code C4 L3 component view as living canon

- Status: proposed
- Date: 2026-05-26
- Supersedes: none
- Source: system-design.md (Components C4 L3, Decisions and trade-offs)

## Context

The `spec-driven-architecture` schema's `system-design` step instructs authors to stop at the container level: "Do NOT go to component (L3) or code (L4) level - that is premature pre-code." <!-- v:fact openspec/schemas/spec-driven-architecture/schema.yaml --> Our reading of that default is that component structure is left to emerge per feature. <!-- v:assumption --> signal-ingestion's D-I already lays out the signals module internals in a feature-local design.md. <!-- v:fact openspec/changes/signal-ingestion/design.md (D-I) --> Ten capabilities remain on the roadmap (#1-#10; only #0 quality-harness and the M0 backbone are done), all building into one app container. <!-- v:derives docs/roadmap.md --> <!-- v:derives docs/architecture/system-design.md --> They share seams already fixed by decision: the D4 `SignalSource` port, the D9 `LLMProvider` port (ADR-0003), the jobs/db/config facades, and the three anchor views - with the D4 `EnrichmentProvider` port planned but not yet specified. <!-- v:derives docs/roadmap.md --> The tension: per-feature emergence risks each capability inventing its own structure with no shared skeleton, while a drawn-up-front L3 risks drifting from the code it describes - a sync hazard analogous to the "sync trap" the README names for reverse capability lists. <!-- v:assumption -->

## Decision

We will deliberately override the schema default and maintain a C4 level 3 component view of the app container as living canon, kept in `docs/architecture/system-design.md` alongside the L1/L2 references. <!-- v:decision --> Because an ADR in `docs/adr/` cannot by itself bind the schema's generation-time instruction, promotion also annotates that schema instruction with a pointer to this ADR and records the override in the architecture README, so a future author reading the schema sees that a pre-code L3 view is intentional here rather than a violation. <!-- v:decision --> The view is a skeleton of the stable seams (ports, facades, role-agnostic cores, anchor-view surfaces, composition root), revised as features land - not a frozen blueprint. <!-- v:decision --> Authority over feature-internal component detail stays with each feature's `design.md`. <!-- v:decision --> The canonical mechanical contract for the seams is the dependency-cruiser port/adapter rule (signal-ingestion D-M), not the diagram. <!-- v:derives openspec/changes/signal-ingestion/design.md (D-M) --> A later change MUST update this view when it adds or moves a component, the same way a change updates any other living-canon doc it touches. <!-- v:derives docs/architecture/README.md (rule 4) -->

## Consequences

Easier: the remaining capabilities build into one agreed module skeleton instead of negotiating structure ad hoc; new contributors see the whole component map and the ports/adapters direction in one place. <!-- v:decision --> Harder: the L3 view is now a maintenance surface - a change that reshapes components must update it, and a stale diagram is a real failure mode. <!-- v:decision --> Mitigation and what bounds the risk: the drift-prone detail (feature internals) is deliberately NOT in this view - it stays in per-feature `design.md` <!-- v:decision --> - and the build-enforced dependency-cruiser rule guards the one seam that matters most (cores and ports must not import adapters), so a drifted diagram misleads but cannot silently break that seam. <!-- v:derives openspec/changes/signal-ingestion/design.md (D-M) --> The db-only and web/worker-share-only-via-Postgres invariants the view also asserts are convention, reviewed not yet build-enforced; a cores-must-not-import-jobs dependency-cruiser rule is a candidate to add when qualification lands, which would mechanize more of the view. <!-- v:decision --> This ADR records the override so the pre-code L3 view is understood as an intentional, scoped exception, not an accident to be "corrected" back to the schema default. <!-- v:decision -->
